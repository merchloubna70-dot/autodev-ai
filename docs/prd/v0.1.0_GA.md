## 1. TL;DR

`autodev-ai` is the Python replacement for [BMAD-METHOD](https://github.com/bmadcode/BMAD-METHOD). Where BMAD asks you to follow a markdown methodology by hand — copy personas, paste prompts, walk the sprint loop yourself — autodev-ai gives you `deliver-project "<one-line brief>"` and runs the whole 12-agent pipeline (PRD → architecture → milestones → tasks → code → tests → release readiness) end-to-end against Codex CLI and Claude Code CLI.

v1.0 ships permissive (MIT, no CLA, never any paid tier) for two audiences: the **individual developer** with a Codex/Claude Max subscription and no PM, and the **2–5 person team** that has no room for a separate planning tool. It is **CLI-first by design** — no IDE plugin, no GUI, no cloud hosting — so it runs anywhere a shell runs: on a laptop, over SSH, inside CI.

v0.1.0 GA cuts when **one non-author files an issue** against the repo. Until then we continue shipping `0.1.0a*` pre-releases. Today (2026-05-14, `v0.1.0a4`) the gate is open at: 0 stars, 0 non-author issues, 0 non-Dependabot PRs.

The cover-image command is **`deliver-project`**. Everything else (`fix-bug`, `roundtable`, `mcp-serve`, `sprint-*`, the Textual dashboard) is "you also get this."

## 2. Problem & target user

### Who v1.0 is for

**Primary — the subscription-rich solo developer.** Has paid for Codex CLI, Claude Pro/Max, or both. Already burns the subscription on day-to-day coding. Wants a planner that converts a one-paragraph idea into an actionable milestone tree without paying for another tool, learning another framework, or signing up for another SaaS.

**Secondary — the 2–5 person team without a PM.** Founders or small product teams where the same person writes the PRD, decomposes tasks, runs the sprint, and reviews the code. They cannot afford a Linear-plus-AI-coding-tool-plus-PM-tooling stack and they should not have to.

**Tertiary — the part-time programmer.** Lawyers, doctors, accountants, researchers shipping side projects. Technical enough to read a stack trace, not interested in becoming a project manager. They want the agent to handle the project-shaped overhead while they make the calls that need a human.

**Tertiary — the existing BMAD-METHOD practitioner.** Already bought into the persona/sprint/milestone methodology. Tired of hand-copying prompts between markdown files. Wants `bmad deliver-project` and there isn't one — so they end up here.

### The four pains v1.0 fixes

1. **Cold-start tax.** Every new project starts with the same unpaid labor: writing a PRD, sketching architecture, listing milestones, decomposing tasks, deciding which CLI to route which task to. CrewAI / AutoGen / LangGraph demos do not survive the path to production. `deliver-project` collapses this into one command + a structured artifact tree.
2. **Multi-CLI scatter.** Codex CLI is excellent at scaffolds and small patches. Claude Code is excellent at architecture and multi-file refactors. Today you eyeball-route — one terminal for Codex, another for Claude, you remember which task is which. `ExecutorRouter` makes the choice deterministic and logs why.
3. **No audit, no resume.** Default agent frameworks emit a stream of tokens and that's it. When the agent burns 100k tokens overnight and produces something wrong, there is no per-step record of *why* it made the call it made. Every run under autodev-ai writes a full artifact tree under `.dev-factory/runs/<run_id>/` and supports `continue-run` and `replay` against it. Network blip or API key rotation no longer means starting from zero.
4. **BMAD-the-methodology has no `bmad deliver-project`.** BMAD-METHOD is a methodology + a prompt library. To actually use it you copy a persona file, paste it into a chat, get an output, paste the output into the next persona's input, and walk the sprint by hand. The methodology is sound; the tooling is human-in-every-loop. autodev-ai is the same methodology, automated, in Python.

### Why not just use X

- **Cursor / Trae (字节) / Qoder (阿里)** — IDE integrations. They assume you are at a desk in front of a GUI. We assume you are on SSH, in a tmux pane, on a CI runner, or in vim. Different surface.
- **OpenHands** — reinvents the agent loop from scratch. Does not reuse your existing Codex CLI / Claude Code subscription. If you already pay for Max, that is a 50–100× cost leverage you would be throwing away.
- **Raw Codex CLI / raw Claude Code** — both are single-command surfaces. Neither knows it is step 5 of a 12-agent pipeline, neither maintains milestone state across calls, neither produces an audit-replayable artifact tree.
- **BMAD-METHOD itself** — the methodology autodev-ai implements. If you are willing to hand-walk personas through a chat UI forever, use BMAD directly. The moment you wish you could script it, you want autodev-ai.

## 3. What v0.1.0 GA ships

### Locked surface

The 14 subcommands present in `v0.1.0a4` are the v1.0 surface. They will not be renamed, removed, or have backward-incompatible flag changes before GA. New flags may be added. New commands may be added. Existing commands' core behavior is frozen.

| Command | Shipped in 1.0 because |
|---|---|
| **`deliver-project`** | Cover-image command. End-to-end brief→release pipeline. |
| `run-issue` | Same pipeline scoped to one GitHub issue. |
| `fix-bug` | 4-stage bug fix (reproduce / locate / patch / verify). |
| `multi-patch-fix-bug` | N-candidate self-consistency for hard bugs. |
| `sprint-start` / `sprint-status` / `sprint-retro` / `sprint-correct` | BMAD-style sprint loop, automated. |
| `roundtable` | A2A multi-agent independent reasoning (party mode). |
| `mcp-serve` | Expose autodev-ai as an MCP server (9 tools) for Claude Desktop / Code. |
| `a2a-serve` / `a2a-call` | A2A HTTP transport for cross-tool agent interop. |
| `investigate` / `generate-context` / `document-project` | Brownfield analysis on existing repos. |
| `continue-run` / `replay` | Resume + replay against the artifact tree. |
| `dashboard` | Textual TUI for run history, sprint retros, roundtable conversations. |

### Locked guarantees

- **Subscription leverage.** `deliver-project --executor auto` routes work to the cheapest correct CLI between Codex and Claude Code. Both must be reachable; otherwise mock executor takes over and the run is marked `NotReleaseReady`.
- **Deterministic mock mode.** Every command works with `--allow-mock-executor true` even when no API keys are present. `release_check` always returns `NotReleaseReady` for mock-tainted runs — a mock run cannot be mistaken for a real one.
- **Artifact tree on every run.** `.dev-factory/runs/<run_id>/{input,product,architecture,planning,execution,quality,verification,delivery}/` is always written. The tree is the source of truth for `continue-run` and `replay`.
- **Strict supply-chain.** Every tag push from v0.1.0a4 onward attaches SBOM (CycloneDX + SPDX), SLSA L3 provenance, and a cosign keyless signature on the GHCR image. v1.0 does not relax this.
- **Strict release-readiness gate.** `release_readiness_gate.py --strict-rc` covers 36 checks (lint, strict mypy, security guardrails, docs, CI parity, packaging). v1.0 cuts only when the gate is at 36/36.
- **MIT, no CLA.** Permanent. Contributors do not sign anything. Forks may take any direction. There will never be a "Pro" tier nor an "Enterprise" tier nor a hosted SaaS.

### CrewAI agent graph

The 12-agent pipeline is the public contract of `deliver-project`:

```
InputClassifier
  → PRDWriter
  → SystemArchitect
  → MilestonePlanner
  → TaskDecomposer
  → ExecutorRouter ──┬─→ Codex CLI
                    ├─→ Claude Code CLI
                    └─→ MockExecutor
  → QualityGate
  → SecurityReviewer
  → Verifier
  → DocWriter
  → ReleaseManager
```

v1.0 preserves the order and the names. Future versions may add agents (always with a flag to opt in/out); they will not remove or reorder these 12.

## 4. What v0.1.0 GA does NOT ship (anti-scope)

This list is binding. v1.0 reviewers reject any PR that introduces or proposes:

- **No cloud hosting.** `autodev-ai` is a binary you run locally or in your CI. There is no `autodev.cloud`. There never will be inside this repo.
- **No GUI.** No Electron app, no web dashboard, no menu bar app. The Textual TUI (`autodev-ai dashboard`) is the only UI; it runs in a terminal.
- **No IDE plugin.** No VS Code extension, no JetBrains plugin, no Cursor integration. If you want IDE-shaped editing, use Cursor/Trae/Qoder; autodev-ai is what you reach for when you are not in an IDE.
- **No enterprise tier.** No paid support contracts, no "Pro" SKU, no "Enterprise" edition with proprietary features, no dual-license open-core. MIT now, MIT at v1.0, MIT after v1.0.
- **No CLA / DCO.** Contributors push PRs; if the PR is good it gets merged. No paperwork.
- **No swap of CrewAI for LangGraph / AutoGen / LlamaIndex.** The 12-agent CrewAI graph is the contract. Forks are free to swap the underlying framework; this repo is not.
- **No first-class adapter for non-Codex / non-Claude-Code CLIs** in v1.0. Gemini CLI, Qwen Code, Trae, Aider — out of scope until v1.x at earliest. The router contract is public; if your favorite CLI is missing, add an adapter in your fork or open an issue.
- **No methodology divergence from BMAD-METHOD.** Sprint, persona, milestone, retro must remain conceptually recognizable to BMAD users. Inventing a new project-management vocabulary is out of scope.
- **No telemetry phone-home.** Zero outbound network calls except to the LLM/CLI endpoints the user explicitly configures.

## 5. Differentiation — why this project is worth contributing to

Framed for a prospective contributor evaluating *"is there room for me to add value here?"*

### vs BMAD-METHOD (the project we are replacing)

| Dimension | BMAD-METHOD | autodev-ai |
|---|---|---|
| Methodology | Sprint / persona / milestone / retro | Same (deliberately) |
| Language | Markdown + manual chat | Python + CLI |
| User loop | Human walks every persona by hand | `deliver-project` walks them automatically |
| Reproducibility | Whatever chat history survives | Full artifact tree, `replay` works |
| CLI integration | None | Codex CLI + Claude Code CLI native |
| Mock / no-key mode | N/A (you are the executor) | Deterministic, marked `NotReleaseReady` |

**For a contributor:** if you like the BMAD methodology and want to write Python instead of more markdown personas, this is the project. The conceptual frame is settled (Q4 / Section 2); the implementation surface is where value gets added.

### vs IDE agents (Cursor / Trae / Qoder)

These tools optimize the "human staring at a code editor" workflow. We optimize the "human reads `git log` from a server" workflow. The two are complementary, not competitive — but contributors should know we will not be pulled into IDE land. PRs that assume a GUI context are out of scope.

### vs OpenHands

OpenHands reimplements the entire agent loop. We treat Codex CLI and Claude Code CLI as paid-for primitives and orchestrate them. A 12-agent run under autodev-ai costs ~$0–5 against an existing Max/Pro subscription; the equivalent OpenHands run hits raw API and can cost 50–100× more. If you have a strong opinion about agent-loop internals, contribute to OpenHands. If you have a strong opinion about subscription leverage and pipeline shape, contribute here.

### vs raw Codex CLI / raw Claude Code

These are excellent primitives, but neither knows it is step N of a pipeline. autodev-ai is the orchestration layer that sits on top. We do not compete with the CLI vendors; we depend on them. If Anthropic or OpenAI ships their own pipeline product, we either become irrelevant (and that is fine — autodev-ai is MIT, fork it forever) or we stay relevant by being the *open-source, multi-vendor, methodology-aligned* alternative.

### What this means for new contributors

The areas with the most slack — i.e. where a thoughtful PR will land — are:

- **More adapters under the router contract** (Gemini CLI, Qwen Code, etc., even though they are not in v1.0 scope, the contract is open).
- **More executors in CI environments** (GitHub Actions, GitLab CI, Drone runners — `deliver-project` working unattended in CI).
- **Better dashboards on the artifact tree** (visualizers, web exporters, code-review-PR-comment generators).
- **More verification gates** (security scanners, performance regression detectors, license auditors plugged into `QualityGate`).
- **Brownfield improvements** (`investigate` and `document-project` accuracy on large legacy codebases).

Anything that grows the surface defined in Section 3 along these axes is on-thesis. Anything in Section 4 is off-thesis.

## 6. GA trigger conditions & release plan

### The single GA gate

**v0.1.0 GA cuts when exactly one (1) issue is filed in `merchloubna70-dot/autodev-ai` by a GitHub account that is not the project author.** Any issue type counts: bug report, feature request, question, "this doesn't install on Arch," anything. The semantic gate is *"someone other than us has touched this enough to file something."*

Why this gate:

- **Honest to current state.** As of 2026-05-14, the repo is 12 hours old. Stars are 0, forks are 0, watchers are 0, non-Dependabot PRs are 0. Inventing a "≥100 stars" trigger would be theater.
- **Highest signal per unit count.** Stars are vanity; an issue takes effort and means someone tried the thing. A single issue is enough proof of "real use" to justify cutting from `a*` to a stable `0.1.0`.
- **Avoids the over-engineering trap of multi-metric triggers.** One concrete number, one Boolean.

The gate is asymmetric: alpha → GA is permitted on this trigger; pulling back from GA later is not blocked by anything in this PRD (we can always cut `0.1.1`, `0.2.0`, etc.).

### The path between now and GA

Continue cutting `0.1.0a*` pre-releases as follows:

- **Cadence:** as needed — there is no calendar. A new alpha cuts when a meaningful change merges (new command, dependency bump that affects users, security patch).
- **Each pre-release runs the full `scripts/release_preflight.sh`** locally before the tag is pushed. R11 surfaced three classes of late-binding bugs (mypy override drift, workflow-extras drift, version-string drift across three surfaces); the preflight script forecloses all three.
- **Each pre-release passes `release_readiness_gate --strict-rc`** in CI as a release blocker. v0.1.0a4 set the precedent at 36/36; v1.0 holds the bar.
- **Each pre-release ships SBOM + SLSA + cosign.** v0.1.0a4 was the first; this is a permanent property of every tagged release.

### GA release mechanics

When the trigger fires:

1. Verify the issuer is not the project author (`gh api ...`).
2. Bump `pyproject.toml` to `0.1.0` (drop the `a*` suffix). Update `Info.plist`, `README.md`, `CHANGELOG.md`. Run `scripts/release_preflight.sh`.
3. Tag `v0.1.0`, push, let workflows publish.
4. Verify post-publish: `pip install autodev-ai==0.1.0` (no `--pre` needed), `docker pull ghcr.io/merchloubna70-dot/autodev-ai:v0.1.0`, Homebrew tap bumped, cosign verifies.
5. Reply to the triggering issue. Thank the issuer. Make sure their issue is actually closeable or has a reasonable next step.

## 7. Success metrics

Reader-aware framing: success here is *"is this project worth a contributor's time?"*, not *"is this project profitable?"* (it can never be profitable — see Section 4).

### Leading indicators (weekly)

- **External issues opened** — the only metric directly tied to the GA gate. Goal: > 0 within the alpha window.
- **Non-Dependabot PRs opened** — strong signal of contributor interest. Goal: > 0 by GA + 8 weeks.
- **PyPI installs delta** — best-effort tracking via `pypistats`. Vanity-adjacent but useful for trend.
- **Stars delta** — pure vanity; tracked only to avoid surprise. Not a gate.

### Lagging indicators (per quarter)

- **External projects delivered with `deliver-project`** — counted by anyone publicly reporting they ran the command and shipped something. Self-reported, low fidelity, high signal.
- **Forks with non-trivial commits** — fork count alone is noise; forks that have actually diverged with new code are real interest.
- **Cross-referenced from BMAD-METHOD community** — appearing in BMAD-METHOD's own README, discussions, or related discourse confirms the "Python replacement" positioning.
- **Unsolicited writeups** — blog posts, talks, Twitter threads not authored by the project owner. Counted, not chased.

### Anti-metrics (we explicitly do not optimize)

- Stars as a goal in themselves.
- Install counts as a goal in themselves.
- "Number of integrations" (against Section 4).
- "Enterprise leads" (against Q7, the entire project's stance on commerce).
- Hacker News front-page placements (against the honest-to-contributors reader profile).

## Appendix A: open decisions left to GA

This PRD locks Q1–Q8 of the original strategic questionnaire (2026-05-14). The following remain open and may invalidate parts of this PRD when answered:

- **Cosign verification UX.** Currently requires the user to know the `--certificate-identity-regexp` incantation. A `scripts/verify_release.sh` wrapper that just takes a version number would lower the bar; not in v1.0 scope unless an external user files an issue about it.
- **Homebrew on Linux.** The tap is published; Linux-side install has not been smoke-tested as of v0.1.0a4 R11 (blocked locally by macOS libexpat ABI drift, unrelated to formula). v1.0 may need a Linux runner check.
- **Multi-arch beyond amd64+arm64.** No demand signal. Not planned.
- **CrewAI version pin.** Currently `crewai>=0.30`. CrewAI upstream may break the agent base classes; we have no compatibility test against newer pre-releases. Add such a job before v1.0 if any CrewAI 1.x signal appears.
